# Бронирование переговорной

Приложение для просмотра расписания и бронирования переговорной «Атлас». Интерфейс на русском языке. Запросы обрабатывает имитация HTTP API на MSW в браузере.

- [Открыть приложение](https://meeting-room-booking-tan.vercel.app/)
- [Открыть Storybook](https://meeting-room-booking-storybook.vercel.app/)

## Что реализовано

Расписание дня показывает занятые и свободные интервалы одним хронологическим списком. Дату можно ввести в поле или переключить кнопками предыдущего и следующего дня. Полностью свободный рабочий день занимает один интервал с 09:00 до 18:00 с подписью «Весь день свободен».

Выбранная дата хранится в URL как `?date=YYYY-MM-DD`. Ссылку можно скопировать: после открытия или перезагрузки приложение покажет тот же день. Кнопки «назад» и «вперёд» браузера восстанавливают предыдущий выбор. Если дата отсутствует или некорректна, приложение открывает сегодняшний день по московскому времени. Ссылка может указывать и на конкретную встречу: параметр `?booking=id` вместе с датой открывает её редактирование, а возврат по истории браузера закрывает редактор.

Нажатие на свободный интервал или кнопку создания открывает форму бронирования. В ней можно задать:

- дату;
- время начала и окончания;
- название встречи, если оно нужно.

Фокус сразу переходит в диалог. Нажатие на предстоящую встречу открывает её редактирование. После успешного сохранения диалог закрывается, расписание обновляется.

Дата в форме редактируется. При её изменении форма сохраняет черновик, загружает бронирования выбранного дня и проверяет пересечения на этой дате. Удаление доступно внутри редактора встречи: отдельный диалог показывает данные встречи и предлагает подтвердить удаление или отменить его.

| Требование                | Поведение приложения                                                                                                               |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Рабочее время             | Бронирование целиком помещается в интервал с 09:00 до 18:00.                                                                       |
| Порядок времени           | Начало строго раньше окончания.                                                                                                    |
| Длительность              | От 30 до 120 минут включительно.                                                                                                   |
| Шаг времени               | Начало и окончание кратны 10 минутам.                                                                                              |
| Пересечения               | Приложение отклоняет пересекающиеся бронирования на одну дату. Соседние интервалы, например 10:00-11:00 и 11:00-12:00, разрешены.  |
| Прошедшее время           | Прошедшая дата доступна для просмотра. Создание и редактирование недоступны; форма ограничивает время по текущим московским часам. |
| Редактирование            | Проверка пересечений исключает бронирование, которое пользователь редактирует.                                                     |
| Конкурентное бронирование | После ответа API `409` приложение повторно запрашивает расписание, показывает сообщение на русском и сохраняет введённые значения. |
| Устаревшие ошибки         | Изменение времени или выбранной даты сбрасывает прежние ошибки. Изменение только названия сохраняет сообщение о конфликте `409`.   |

Клиент и MSW проверяют интервалы одним валидатором. Для загрузки, ошибки запроса и отправки формы есть отдельные состояния. Пустое расписание будущего дня показывает свободный рабочий интервал.

После ошибки загрузки пользователь может повторить запрос.

Если бронирование сохранено, а обновление расписания не удалось, повтор запрашивает расписание без повторного сохранения. Ответ из закрытого редактора обновляет расписание и сохраняет новый открытый черновик. При переносе встречи на другую дату ответы, пришедшие в обратном порядке, не возвращают устаревшие данные в кеш.

При запуске и загрузке расписания приложение показывает один и тот же скелетон списка. При сбое запуска остаются сообщение об ошибке и кнопка повтора.

Интерфейс поддерживает светлую и тёмную темы и адаптируется к мобильной, планшетной и настольной ширине.

Ручной выбор темы сохраняется в `localStorage` браузера и применяется до первого отображения страницы. Пока ручной выбор не сохранён, приложение следует системной теме.

Явно заданная тема истории Storybook, в том числе вложенная, имеет приоритет и не зависит от сохранённой темы приложения.

У полей есть подписи, у элементов управления есть видимый фокус и управление с клавиатуры.

## Ограничения демо

MSW хранит синтетические записи в `localStorage` браузера: созданные и изменённые брони переживают перезагрузку страницы. Исходные встречи относятся к `2026-10-23`; на других датах список изначально пуст. Сбросить демо можно, очистив данные сайта в браузере. Истории Storybook работают без сохранения: каждый сценарий получает исходный набор встреч.

Приложение использует реальные часы и часовой пояс комнаты `Europe/Moscow` (UTC+3), независимо от часового пояса браузера. Московское время используют:

- сегодняшняя дата и доступность интервалов;
- проверка перед отправкой;
- mock API.

Открытая форма обновляет доступность с течением времени; при отправке время проверяется заново. Фиксированные часы применяются только в Storybook и тестах.

Приложение не подключено к реальному серверу бронирований.

## Локальный запуск

Используйте Node.js 24 из `.nvmrc` и npm.

```sh
npm ci
npx playwright install chrome
npm run security:install-hooks
npm run dev
```

Приложение: <http://127.0.0.1:3000>. MSW запускается до монтирования расписания.

Storybook запускается отдельно:

```sh
npm run storybook
```

Откройте [рабочую область в Storybook](http://127.0.0.1:6006/?path=/story/preview-booking-workspace--default). В разделе UI Kit находятся общие компоненты, в Business rules находятся сценарии валидации и восстановления после ошибок.

Для полного набора проверок нужны Git, Gitleaks 8 и работающий Docker. Требования к инструментам и поведение сканеров описаны в [SECURITY.md](SECURITY.md).

## Сборка и публикация

Локальная сборка и запуск готового Next.js-приложения:

```sh
npm run build
npm run start
```

Приложение открывается по адресу <http://127.0.0.1:3000>.

Приложение и Storybook размещаются в отдельных проектах Vercel. HTTP-запросы приложения обрабатывает MSW в браузере. Команда `npm run build-storybook` собирает Storybook в `storybook-static/`, включая конфигурацию его публикации.

### Проверки в CI

Запрос на слияние должен пройти обязательную проверку `complete-snapshot` процесса `Quality`. Она публикуется и для PR с одной документацией.

CI определяет изменения относительно базового коммита PR или предыдущего коммита `main`:

- unit-тесты и Storybook всегда выполняются полностью;
- Playwright выбирает связанные e2e-файлы через `--only-changed`;
- изменения только README, документации или unit-тестов не запускают e2e;
- общие стили, маршруты, конфигурация браузерного окружения и зависимости требуют полного e2e-прогона;
- если базовый коммит недоступен или связи нельзя определить надёжно, выполняется весь набор.

Выбор e2e учитывает импорты тестов и вспомогательных файлов. Модули, которые приложение загружает через страницу браузера, могут отсутствовать в этом графе. Поэтому для нескольких изменённых runtime-файлов или исходника без связанных тестов используется полный прогон.

Полный e2e-прогон делится на четыре шарды, которые выполняются параллельно на отдельных runner'ах; каждая шарда публикует собственный отчёт. Небольшие выбранные наборы выполняются одной джобой.

Пустой набор разрешён только как явный результат планировщика. Ошибки выбора, пропущенные выбранные файлы и нестабильные тесты блокируют CI. Все e2e сохраняют мобильную, планшетную и настольную ширину.

Каждый сайт собирается один раз за запуск CI. В PR приложение проходит обычную сборку Next.js. В доверенном запуске для `main` команда `vercel build --prod --standalone` создаёт `.next`, `.vercel/output` и `.vercel/project.json`. Тесты используют артефакты этой сборки; Storybook тоже передаёт свою готовую сборку в браузерные проверки.

### Выпуск в production

После успешных проверок изменения, затрагивающие браузерные сценарии, проходят выпуск через окружение GitHub Actions `production`:

1. Выпуск скачивает проверенные артефакты приложения и Storybook. Готовые файлы Storybook упаковываются в Build Output v3 без повторной компиляции.
2. Оба сайта публикуются с `--prebuilt --prod --skip-domain`. На этом шаге публичные production-домены ещё не переключаются.
3. Smoke-проверки обоих сайтов и выбранные e2e выполняются на неизменяемых URL новых deployments.
4. Перед переключением сохраняются ID предыдущих production deployments. Затем приложение и Storybook по очереди получают production-домены через `promote`.
5. Smoke-проверки повторяются на публичных адресах.

Переключение двух проектов выполняется последовательно. При ошибке или отмене выпуск пытается восстановить все сайты, для которых начал переключение. Состояние выпуска сохраняется между шагами, чтобы откат мог использовать записанные deployment ID. Если откат не удался, выпуск сообщает об ошибке и сохраняет состояние для восстановления.

Команда `node scripts/deployment/cli.mjs release` предназначена для workflow. Локальный pre-commit проверяет код и сборки без удалённой публикации. Ручной запуск процесса `Quality` через `workflow_dispatch` на `main` повторяет выпуск без нового коммита — например, после смены секретов или настроек защиты Vercel.

Ветка `main` требует запрос на слияние. Защита действует и для администраторов; принудительная отправка и удаление ветки запрещены. Локальный хук pre-commit блокирует прямой коммит в `main`.

### Проверки опубликованных сайтов

Их можно запустить отдельно:

```sh
npm run test:deployment
npm run test:staging
```

Обе команды требуют:

- `DEPLOYMENT_URL` с адресом приложения;
- `STORYBOOK_DEPLOYMENT_URL` с адресом Storybook.

Если адрес указывает на защищённый URL deployment — например, свежий candidate до переключения домена, — дополнительно задайте `VERCEL_APP_BYPASS_SECRET` и `VERCEL_STORYBOOK_BYPASS_SECRET` со значениями Protection Bypass for Automation из настроек соответствующих проектов Vercel. Публичные production-домены работают без этих переменных.

`test:deployment` проверяет доступность и основные действия на обоих сайтах. `test:staging` выполняет все бизнес-сценарии на опубликованном Storybook.

Эти проверки запускаются отдельно от локального pre-commit и не входят в `check:working-copy`.

## Стек и структура

Приложение использует Next.js App Router, React, TypeScript, Tailwind CSS, shadcn UI, TanStack Query, Zustand, i18next и MSW. Storybook показывает компоненты и состояния интерфейса; Vitest и Playwright проверяют поведение.

Маршруты в `app/` передают рендеринг FSD-слоям в `src/`:

```text
_app → _pages → widgets → features → entities → shared
```

Импорты направлены в нижние слои через публичные API слайсов.

- Компоненты отображают интерфейс;
- Хуки в `model` управляют запросами, состоянием и взаимодействиями;
- Общие компоненты в `shared/ui` оборачивают примитивы shadcn;
- `cn` объединяет классы через `clsx` и `tailwind-merge`;
- Цвета тем заданы семантическими токенами в `src/_app/styles/tokens.css`.

`shared/api` содержит один типизированный клиент на нативном `fetch`. API-модуль бронирований использует этот клиент, TanStack Query хранит серверное состояние. Мутации не повторяются автоматически. MSW перехватывает тот же HTTP-транспорт, который использует приложение.

Zustand хранит черновики формы и выбранную дату. Каждая рабочая область и редактор получают отдельное хранилище. Типизированные хуки принимают селектор; именованные хуки для чтения состояния и вызова действий находятся в `model/selectors.ts`.

Сейчас приложение содержит только русский словарь. Вложенные ресурсы i18next объединяют тексты интерфейса, историй и демо-записей. TypeScript проверяет ключи переводов, а `check:i18n` проверяет рекурсивные ключи и параметры интерполяции относительно русского словаря при добавлении других локалей.

## Интерфейс HTTP

По умолчанию клиент использует базовый путь `/api`. MSW обрабатывает следующие запросы:

| Метод и путь                        | Действие                                                |
| ----------------------------------- | ------------------------------------------------------- |
| `GET /api/bookings?date=YYYY-MM-DD` | Получить бронирования за день в порядке времени начала. |
| `POST /api/bookings`                | Создать бронирование.                                   |
| `PATCH /api/bookings/:id`           | Изменить бронирование.                                  |
| `DELETE /api/bookings/:id`          | Удалить бронирование.                                   |

Данные формы содержат `date`, `start`, `end` и необязательный `title`.

- При пересечении API возвращает `409`.
- При другой ошибке валидации или некорректном теле запроса API возвращает `400`.
- Типизированный доменный код ошибки определяет сообщение формы.

Для подключения реального сервиса нужно заменить запуск MSW и настроить `NEXT_PUBLIC_API_BASE_URL`, сохранив контракт запросов и ответов.

## Проверки

Полная проверка рабочей копии:

```sh
npm run check:working-copy
```

Команда создаёт отдельный снимок исходников и запускает:

- Gitleaks;
- Semgrep в Docker;
- проверки локалей, типов, ESLint, границ FSD и структуры файлов;
- React Doctor, проверку форматирования и поиск неиспользуемого кода;
- unit/integration-тесты, браузерные проверки Storybook и Playwright;
- сборки приложения и Storybook.

По умолчанию одновременно работают не более двух независимых веток, в каждой используется один процесс для тестов и сборки.

Хук pre-commit проверяет полный снимок индекса Git и всегда запускает все e2e. Переменная выбора CI не может сократить локальную проверку коммита.

GitHub Actions запускает команды из общего `validationCommands` в отдельных jobs:

- правила кода;
- безопасность;
- unit/integration;
- Storybook;
- две сборки;
- выбранные e2e;
- визуальное сравнение с эталонными скриншотами.

Независимые jobs работают на отдельных runners. Сборки передают артефакты браузерным тестам внутри того же запуска. Итоговый `complete-snapshot` проверяет результаты всех jobs и блокирует слияние при ошибке, отмене или неожиданном пропуске.

Визуальная проверка запускает собранный Storybook в закреплённом Docker-образе Playwright и сравнивает его с PNG в репозитории. При отличиях job падает и сохраняет HTML-отчёт, фактические снимки и diff. Отдельный сервер не нужен. Порядок запуска и обновления эталонов описан в [инструкции](docs/visual-regression.md).

Проверяющие команды не добавляют файлы в индекс и не создают коммиты.

Отдельные команды:

```sh
npm test
npm run test-storybook
npm run test:e2e
npm run check:i18n
npm run typecheck
npm run build
npm run build-storybook
```

Модульные тесты лежат рядом с проверяемыми модулями в папках `__spec__`. Сценарные данные вынесены в именованные константы и соседние `*.fixtures.ts`.

ESLint запрещает магические бизнес-значения в коде и строковые данные в вызовах ввода и проверках текста. API-ошибки предоставляют смысловые проверки, например `isConflict`, вместо сравнения HTTP-статусов в UI.

Проверки разделены по уровню:

- модульные тесты проверяют правила интервалов, построение расписания дня, доступность времени, переходы состояния интерфейса и инструменты проверки проекта;
- интеграционные тесты проверяют HTTP-клиент и API бронирований с MSW;
- Storybook запускает браузерные проверки и проверки доступности;
- Playwright проверяет пользовательские сценарии.

Оба набора браузерных тестов работают на мобильной, планшетной и настольной ширине.

`play`-функции историй только переводят интерфейс в нужное состояние. Утверждения находятся в test/spec-файлах. Тесты обращаются к элементам через импортированные константы `data-testid`.

Истории и их вспомогательные сценарии находятся в папках `stories/` рядом с компонентами. ESLint проверяет размещение stories и unit-тестов, а также запрещает рабочему коду импортировать файлы из `stories/`. Эти правила выполняются в обязательном шаге `lint` общего pre-commit.

Покрытие кода приложения можно измерить отдельно для unit/integration и Storybook:

```sh
npm run test:coverage
open coverage/unit/index.html

npm run test:coverage:storybook
open coverage/storybook/index.html
```

Отчёты показывают покрытие строк, веток и функций, включая файлы приложения, которые тесты не исполняли. В HTML можно открыть файл и увидеть непокрытые строки.

Код историй, тесты, объявления типов и test ID исключены из метрики. Результаты unit/integration и Storybook хранятся отдельно; E2E в эти проценты не входят.

Команда `open` открывает отчёт на macOS; на других системах откройте HTML-файл в браузере.
